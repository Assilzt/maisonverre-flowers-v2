# Orders, Telegram and EcoTrack

## Checkout compatibility

الحفاظ على منطق الزهور أولوية: Draft capture بعد كتابة الهاتف مع Debounce، Lead عند رقم صالح، InitiateCheckout وPurchase وفق توقيت المصدر الأصلي. Purchase يُرسل فقط بعد نجاح حفظ الطلب، فلا تُحتسب محاولة فاشلة كتحويل. الطلب يحفظ طريقة التوصيل (`home` أو `stop_desk`) ورسومها المحسوبة على الخادم؛ مكتب الشحن متاح فقط للبلديات التي تملكه. Draft لا يُرفض إذا تعذر تحميل رسوم التوصيل. Preview وAdmin لا يرسلان أحداث Pixel.

Lead ID مع Capability token يحددان نفس Draft. Token يُخزن كـHash في Database. SQL يكتب الطلب وOutbox معًا، يمنع تكرار Lead وتراجع Complete إلى Abandoned، ويحمي الطلب المؤكد أو المشحون من تحديثات المتصفح المتأخرة. الخادم يتحقق من Quantity والعرض المنشور ورسوم التوصيل.

## Telegram isolation

الـWorker يقرأ Outbox بعد الحفظ. رسالة الطلب تُنشأ على الخادم، ويُستخدم message_id لتحديثها عند الإمكان. توجد Lease وBackoff وحد للمحاولات؛ شاشة **المهام والأخطاء** تعرض الفشل وتسمح بإعادة المحاولة. Scheduler مستقل مطلوب حتى لو أُغلقت الإدارة.

إذا قبل Telegram رسالة ثم انقطع الاتصال قبل تسجيل message_id فقد تتكرر الرسالة؛ لا ندّعي Exactly once. لا يمكن ضمان حفظ الطلب إذا تعطلت قاعدة البيانات نفسها بالكامل.

## Meta Conversions API

يرسل الخادم نسخة من أحداث Meta المهمة، ويستعمل Meta معرّف `event_id` المشترك ليحتسب كل حدث مرة واحدة:

| الحدث            | متى                                                            | `event_id`           |
| ---------------- | -------------------------------------------------------------- | -------------------- |
| `Lead`           | أول حفظ Draft برقم هاتف صالح (والمتصفح يرسل Lead بنفس المعرّف) | `lead.<leadId>`      |
| `Purchase`       | حفظ الطلب المكتمل (والمتصفح يرسل Purchase بعد الحفظ)           | `purchase.<leadId>`  |
| `OrderConfirmed` | تسجيل نتيجة الاتصال «مؤكد» لأول مرة                            | `confirmed.<leadId>` |
| `OrderDelivered` | أول مزامنة تبلغ حالة سُلّمت/دُفعت                              | `delivered.<leadId>` |
| `OrderReturned`  | أول مزامنة تبلغ حالة مرتجع                                     | `returned.<leadId>`  |

- البيانات الشخصية (الهاتف بصيغة `213…`، الاسم، البلدية، الولاية، البلد) تُرسل مشفرة SHA-256. IP وUser agent و`_fbp`/`_fbc` تُرسل كما هي حسب قواعد Meta.
- عند حفظ الطلب يُخزَّن سياق متصفح العميل في `atlasio_orders.meta_context`، لتستعمله أحداث التأكيد والتسليم لاحقًا بدل متصفح المشرف. يُحذف عند الحالة النهائية أو بعد 30 يومًا.
- الأحداث في جدول `mv_capi_events` مع إعادة محاولة تدريجية؛ تُعتبر فاشلة بعد 8 محاولات أو عند رفض نهائي من Meta، وتنتهي صلاحيتها بعد نحو 7 أيام. تُحذف الحمولة بعد الإرسال.
- بدون Access token لا يُخزَّن أي حدث ولا أي سياق.

## Shipment lifecycle

1. تأكيد الطلب قبل الشحن. تحديد Provider وStock أو Without stock.
2. Claim ذري يمنع طلبين متزامنين من إنشاء نفس الشحنة. Quantity تؤخذ من الطلب المحفوظ. حجز المخزون مشروط بتوفره.
3. Tracking المقبول فقط يربط الشحنة. فشل مؤكد يحرر الحجز؛ Timeout/Network/5xx أثناء الإنشاء أو نجاح بلا Tracking يُعامل كـUncertain.
4. Recovery يبحث بالمرجع لدى الشركة ثم يربط الشحنة المثبتة. عدم العثور لا يعني أن إعادة الإنشاء آمنة تلقائيًا.
5. Sync يستخدم Trackings المعروفة لكل حساب في Batches، مع آخر محاولة وآخر نجاح وتاريخ الحالة. لا يُرجع الرد القديم الحالة للخلف عند توفر تاريخ قابل للمقارنة.
6. حالة الطلب وحالة الشحنة والدفع مستقلة. En livraison لا تعني تم التسليم، وEncaisse non payé أوPaiements prêts لا تعني دفع أموال البائع. الحالة غير المعروفة تظهر بنصها بدل اختراع معنى.

الأزرار: التحديث، اعتماد الشحنة مع/دون Ramassage، تعديل قبل الاعتماد حيث تسمح الشركة، ملاحظة، ملصق PDF، طلب إرجاع، تأكيد استلام المرتجع وإلغاء الشحنة. تُراجع الحالة البعيدة قبل الإجراءات الجديدة. لا يوجد زر يحاكي Scan إيداع أو تسليم مادي غير متاح عبر API. إلغاء الشحنة وتحرير المخزون المحلي ذريّان، فلا تتضاعف الكمية عند تكرار الإلغاء.

مرجع التكامل: [EcoTrack Postman API](https://documenter.getpostman.com/view/14517169/Tz5je15g). كل حساب قد يختلف في البيانات والصلاحيات؛ اعتماد التكامل الحقيقي يتطلب Staging token وطلبات اختبار.
